# Задание 5. Разработка cutover-плана

## 1. Анализ текущей ситуации

Текущая система компании Medikamente обладает следующими характеристиками:
- данные хранятся в Excel файлах
- используется 1С в файловом режиме
- система работает на одном физическом сервере
- отсутствуют API и централизованная БД
- нет автоматизации бизнес-процессов

При росте компании такая архитектура становится узким местом:
- сложно масштабировать
- высокая вероятность ошибок
- проблемы безопасности данных
- невозможность интеграций

### Цель миграции

Создать современную архитектуру системы:
- централизованная БД (PostgreSQL)
- микросервисная архитектура
- API-интеграции
- клиентский портал
- аналитическая платформа

## 2. Выбор стратегии миграции

Рассматривались три стратегии

| Стратегия             | Описание                                                    | Ограничения                     |
| --------------------- | ----------------------------------------------------------- | ------------------------------- |
| High-level design     | полная разработка новой архитектуры и одновременный переход | высокий риск                    |
| Parallel run          | параллельная работа старой и новой системы                  | сложная синхронизация           |
| Branch by abstraction | постепенный перенос функциональности                        | требует архитектурных изменений |

### Выбранная стратегия

#### Parallel run

Причины выбора:
- минимизация риска остановки бизнеса
- возможность тестирования новой системы в реальных условиях
- постепенный перевод пользователей
- возможность быстрого rollback

Ограничения стратегии:
- необходимость синхронизации данных
- временное увеличение нагрузки на инфраструктуру
- сложность поддержки двух систем

## 3. Cutover-план миграции

Миграция выполняется поэтапно


| Этап | Описание действия                 | Ключевые задачи                      | Ответственные      | Сроки     | Риски и меры                          |
| ---- | --------------------------------- | ------------------------------------ | ------------------ | --------- | ------------------------------------- |
| 1    | Подготовка инфраструктуры         | развертывание Kubernetes, PostgreSQL | DevOps, архитектор | 2 недели  | ошибки конфигурации -> тестовая среда |
| 2    | Подготовка новой архитектуры      | разработка микросервисов             | backend            | 4 недели  | ошибки архитектуры -> code review     |
| 3    | Миграция данных                   | перенос данных из Excel и 1C         | DBA                | 2 недели  | потеря данных -> backup               |
| 4    | Настройка интеграций              | API лаборатории и платежей           | backend            | 2 недели  | нестабильность API                    |
| 5    | Запуск parallel run               | одновременная работа систем          | DevOps             | 3 недели  | рассинхронизация данных               |
| 6    | Постепенный перевод пользователей | перевод сотрудников на новую систему | IT отдел           | 2 недели  | обучение пользователей                |
| 7    | Мониторинг системы                | анализ производительности            | DevOps             | постоянно | деградация производительности         |
| 8    | Полный переход                    | отключение старой системы            | CTO                | 1 неделя  | критические ошибки                    |

## 4. Критические моменты

### Миграция данных

Основной риск:
- потеря данных
- несоответствие форматов

Меры:
- резервное копирование
- проверка целостности данных

### Синхронизация систем

Во время parallel run:
- данные должны быть одинаковыми

Решение:
- использовать ETL процессы
- использовать event-based синхронизацию

### Производительность

Новая архитектура может иметь проблемы:
- сеть
- микросервисные вызовы

Меры:
- нагрузочное тестирование
- мониторинг

## 5. Роли участников

| Роль            | Ответственность              |
| --------------- | ---------------------------- |
| Архитектор      | разработка архитектуры       |
| DevOps          | инфраструктура и деплой      |
| Backend команда | разработка сервисов          |
| DBA             | миграция данных              |
| QA              | тестирование системы         |
| CTO             | финальное решение о переходе |

## 6. Управление рисками

| Риск                          | Вероятность | Влияние     | Меры             |
| ----------------------------- | ----------- | ----------- | ---------------- |
| потеря данных                 | средняя     | критическое | резервные копии  |
| деградация производительности | средняя     | высокое     | мониторинг       |
| ошибки интеграции             | высокая     | среднее     | тестирование API |
| ошибки пользователей          | высокая     | низкое      | обучение         |

## 7. План отката (Rollback Plan)

Если новая система работает нестабильно:
1. Остановка новой системы
2. Переключение пользователей на старую систему
3. Восстановление данных из backup
4. Анализ ошибок

## 8. Мониторинг после миграции

Используются инструменты:
- Prometheus
- Grafana
- Victoria Metrics
- ELK Stack

Контролируются:
- нагрузка на сервисы
- ошибки API
- время ответа
